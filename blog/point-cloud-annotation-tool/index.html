Designing the Point-Cloud Annotation Loop

One scene, one instance, sixty-six frames—and no context lost between them

Yan haixu Aug 16, 2026
  • Start from the record
  • Scene Mode
  • The state timeline
  • Focus Mode
  • Problem vs. normal
  • The QA loop
  • Interaction rules
  • Visual language

A 3D box is not the final unit of work. It is one observation of an object track. What eventually matters is whether the same object keeps the right class, position, extent, orientation, visibility, and quality state across time. A fast drawing tool can still produce poor data if it makes those relationships hard to inspect.

The interface was therefore designed from the data record outward. Every region on screen exposes one part of the same object, rather than behaving like an independent feature.

THE RECORD instance@frame = class + pose + extent + evidence + review_state track = instance[t₀ … tₙ]

The projections expose pose and extent. The instance list exposes identity and class. The timeline exposes the track. The issue markers and color states expose review. This is the first constraint of the design: changing the active instance or frame must update every representation together. The operator should never have to reconcile two selections or wonder which panel is stale.

01 / SCENE MODEBuild the scene before following the track

Scene Mode answers a broad question: what exists at this timestamp, and is the scene internally consistent? The main viewport preserves spatial relationships between truck heads, trailers, cranes, plates, vehicles, cones, pedestrians, and unknown objects. Three orthographic projections sit beside it because a box that looks plausible in perspective can still be too wide, too tall, or offset from the returns.

  1. 01
    Instance indexThe list is the stable address of every object. Class icons and colors accelerate scanning; the selected row is a single global selection.
  2. 02
    Orthographic evidenceTop, side, and front projections turn an ambiguous 3D fit into three simpler boundary checks.
  3. 03
    World contextThe large scene reveals collisions, duplicated boxes, implausible scale, and objects assigned to the wrong physical structure.
  4. 04
    Numerical definitionClass, position, size, rotation, difficulty, point count, and instance ID remain visible without opening a separate form.
  5. 05
    Temporal footprintThe bottom strip shows whether the selected object is normal or problematic before the operator leaves the frame.

Red question markers are placed directly in the 3D scene. The corresponding issue list on the right carries the description and affected frame range—for example, frames 23–30. Location and explanation are deliberately separated but linked: the scene answers where; the issue panel answers what changed and who resolved it.

The unknown class is also a deliberate output, not an escape hatch. Sparse returns and occlusion often make a confident class impossible. Preserving uncertainty is better than forcing a clean but incorrect label into the dataset.

02 / CORE INNOVATIONThe timeline is a state matrix, not a media scrubber

A conventional player answers only “which frame am I viewing?” That is insufficient for annotation. The useful question is “which objects exist, over which intervals, and where are the exceptions?” The timeline encodes that query directly: columns are frames, rows are object classes or tracks, and each cell carries state.

The red and blue segments are the essential contract. Red means that the frame contains a known problem. Blue means that the frame is normal. Because the encoding forms contiguous runs, a temporal failure becomes visible as a shape: a short red interval suggests a local exception; a long interval suggests a track-level problem; a one-frame red cell inside a blue run suggests a discontinuity worth inspecting immediately.

This changes navigation from playback to lookup. The operator first scans the matrix, then jumps to the relevant cell. That cell resolves a tuple—object, frame, quality state—and should drive the rest of the workspace:

(instance_id, frame_id) → scene + projections + attributes + issue

The vertical playhead gives an exact frame. The aggregate strip above the grid gives a sequence-level summary. The object rows show where that summary comes from. The same status is therefore readable at three scales without opening a report: dataset sequence, object track, and individual frame.

03 / FOCUS MODEHold one instance still; let time move around it

Scene Mode is the right place to establish context, but it is inefficient for checking temporal consistency. Focus Mode inverts the workspace: one instance remains fixed while its frames are laid out as comparable cards. Each card repeats the same three projections, frame number, difficulty, and yaw value.

The card grid makes several failure modes visually cheap to detect. A box that changes width for one frame becomes a broken rhythm. A yaw jump becomes a numerical outlier beside otherwise stable values. A missed frame becomes a hole in the sequence. Difficulty can be assigned where the evidence is visible instead of in a detached metadata form.

The selected frame receives a blue border and footer, while the global timeline remains at the bottom. This preserves orientation when moving between modes. Scene Mode and Focus Mode are not two tools; they are two projections of the same state. The mode switch changes the comparison axis, not the underlying selection.

Review discussion is attached to the affected card. The reviewer can describe the issue, the annotator can repair it, and the interface records confirmation in place. The evidence, conversation, and resolution do not drift into separate systems.

04 / FRAME STATEProblem and normal must be distinguishable before opening the frame

The following two screens show the same workspace at different timeline positions. The geometry tools do not change. The state encoding does. This is important: quality is not another mode that replaces the annotation interface; it is data carried by the same frame and object records.

In the problem state, the active playhead intersects a red segment. In the normal state, it intersects a blue segment. That relationship is repeated in the sequence summary and object row, so status survives both a quick peripheral glance and a detailed inspection. Color is not decoration here; it is an index into the repair workload.

The design avoids recoloring the point cloud itself to express QA. Point colors and box colors already encode geometry and class identity. Overloading them with review status would destroy information. Quality therefore lives in the timeline, markers, and issue panel—surfaces where red and blue have an unambiguous meaning.

05 / QA LOOPSeparate local defects from task-level acceptance

A frame can contain a problem while the annotation task is still in progress. An instance can be repaired while the full sequence is not yet accepted. The interface keeps these levels distinct. Frame cells carry local state; issue records carry repair state; the top bar carries task state.

Annotation complete→QA review→Failed + issue→Repaired→Data qualified

This prevents one overloaded “done” flag from hiding important transitions. A failed review creates a concrete issue and frame range. Repair changes the local record. Re-review changes the task state. Final acceptance becomes traceable because each transition has evidence behind it.

06 / INTERACTIONRules that make the tool teach itself

  • Selection is global.There is one active instance and one active frame. Every panel consumes that state.
  • Time is directly addressable.The operator jumps to a frame-state cell instead of searching through playback.
  • Errors can be intervals.A problem across frames 23–30 is one temporal issue, not eight disconnected comments.
  • Evidence stays beside the decision.Difficulty, yaw, attributes, and repair discussion appear where the point evidence is being judged.
  • Uncertainty remains valid data.unknown prevents low-confidence guesses from becoming false certainty.

These rules reduce training time because they remove exceptions from the interaction model. Selecting from the list, the viewport, a card, or a timeline cell always converges on the same object-frame pair. Once that relationship is understood, the rest of the interface becomes predictable.

07 / VISUAL SYSTEMThe studio stays quiet so the data can be loud

The interface uses the compact, direct feel of a modern design tool: low chrome, one-pixel boundaries, shallow hierarchy, icon-led controls, and immediate selection feedback. The dark canvas is not a theme choice. It is a contrast budget for sparse points, wireframes, labels, and overlapping 3D boxes.

Saturated colors belong to object identity. Blue and red belong to quality state. Gray belongs to structure. Keeping those channels separate is what allows a dense screen to remain readable. The UI can show more because each color has a narrow job.

A good annotation tool behaves like a debugger for data: inconsistency is cheap to find, its cause stays visible, the correction is local, and the final state is auditable.

The design is complete when operators stop thinking about panels and begin moving directly between evidence, exception, and repair.
