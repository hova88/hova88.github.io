Designing for Flow:
A Point-Cloud Annotation Tool

How a dense 3D workflow became a calm, learnable studio for operators

Yan haixu Aug 16, 2026
  • Designing for repetition
  • One workspace
  • Two modes, one grammar
  • Linked views
  • Instances and attributes
  • Time as structure
  • Quality in context
  • A light studio language

Point-cloud annotation is not one difficult action. It is a long sequence of small, precise decisions: find an object, understand its geometry, choose a class, fit a box, move one frame forward, check continuity, and repeat. A tool can support every individual action and still feel exhausting if it asks the operator to repeatedly relocate attention, reopen context, or remember hidden state.

That observation became the central design premise for this studio: the next necessary action should already be near the operator's attention. The interface is not optimized for the elegance of a single screenshot. It is optimized for the rhythm of an eight-hour session, when every extra click, long pointer journey, and ambiguous status becomes real cognitive cost.

The operating principle

Reduce mode switches. Preserve spatial memory. Keep the object, its geometry, its time, and its quality state in one continuous field of view.

The result is deliberately dense, but not busy. Density is useful when information has a stable home. The design keeps a professional operator's entire loop visible while giving each region a single responsibility. Once that geography is learned, the interface begins to disappear.

01 / WORKSPACEOne workspace, one mental model

The studio is organized as a persistent spatial model. Objects live on the left. Geometry occupies the center. Properties and review issues live on the right. Time runs along the bottom. Workflow state sits above everything. These regions do not trade places when the task changes, so the operator never has to rebuild a mental map.

1InstancesFind, filter, and select every object in the scene.
2Detail viewsFit edges precisely in three orthographic projections.
33D sceneUnderstand the object in its full spatial context.
4InspectorEdit labels, geometry, difficulty, and review issues.
5TimelineSee presence, continuity, frame state, and the current playhead without leaving the scene.

The layout follows the natural direction of the work. Selection begins on the left, verification happens in the center, correction happens on the right, and progression happens below. The large 3D viewport receives the most space because spatial judgment is the highest-value task. Supporting panels remain narrow and predictable.

Global state is visible, not buried

The top bar carries the few states that affect the whole task: annotation mode and the route from annotation complete to quality passed, quality failed, and data accepted. This makes state a part of the working surface rather than an administrative screen visited afterward. Operators can tell where they are in the pipeline without interrupting the job.

02 / MODESTwo modes, one interaction grammar

Point-cloud work alternates between two different questions: “What objects exist in this frame?” and “How does this object behave across frames?” The studio makes that distinction explicit through two primary modes while keeping the surrounding interface unchanged.

MODE 01

Single frame · multiple instances

Optimized for scene coverage. The operator scans one timestamp, creates or adjusts every visible instance, and compares nearby objects in context.

MODE 02

Single instance · multiple frames

Optimized for continuity. Attention narrows to one object while the timeline reveals its motion, persistence, and frame-to-frame consistency.

The important design decision is what does not change. The instance remains the same concept. Selection uses the same highlight. The inspector preserves the same field order. The timeline stays in the same place. Switching modes changes the scope of attention, not the language of the product. That continuity lowers the training cost and prevents mode errors.

03 / GEOMETRYLinked views replace mental arithmetic

A 3D bounding box can look correct from one angle and be clearly wrong from another. The studio therefore treats the main perspective view and three orthographic views as one instrument. Selecting an instance in any region activates it everywhere: list row, colored box, projection, label, attributes, timeline track, and review markers.

A
Overview for meaning

The central 3D scene answers “What is this object, and where is it relative to everything else?”

B
Projections for precision

The stacked side views answer “Do the box edges actually fit the observed points?”

C
One selection everywhere

No panel creates a second context. Every view is simply another lens on the active instance.

This coupling removes a surprisingly expensive task: mentally translating between a list item, a colored cuboid, three projections, and a row of numeric values. The system performs that translation continuously. The operator can spend attention on judgment instead of bookkeeping.

04 / OBJECTSThe instance list is a set of handles, not a database

The left panel is intentionally compact. Names such as truck_head_big 1, ego_trailer 1, stacker 8, or unknown 1 combine class and instance identity in a form that can be scanned quickly. Small class icons and persistent colors make the list readable before the text is fully parsed. The selected row uses a broad blue highlight, giving the eye an immediate anchor in a visually complex scene.

The taxonomy covers the real operational world—from truck heads, trailers, hatch plates, stackers, cones, and cranes to general vehicles and pedestrians—but the list remains visually flat. Hierarchy is introduced only when it accelerates selection. The interface does not make the operator navigate an ontology before touching the object.

The inspector orders fields by decision frequency

On the right, the label appears first, followed by geometry and then descriptive metadata. Position, size, and rotation repeat the same x/y/z pattern, so the operator learns one numeric grammar. Annotation difficulty, point count, and instance ID sit below because they explain or verify the object rather than define its geometry.

05 / TIMEThe timeline turns frames into structure

A frame counter tells the operator where they are. A timeline explains what is happening around them. The lower region combines a frame ruler, a clear playhead, a global progress strip, and one track per relevant object. Contiguous blocks reveal when an instance exists, when it has been handled, and where attention is still required.

The timeline also solves navigation without adding another mental model. Clicking a frame changes the shared scene context; selecting a track changes the shared instance context. Time and object are the two axes of the task, and the tool makes both directly addressable.

Frame-range feedback stays a range

When a problem extends across frames 23–30, the system preserves it as a temporal range instead of duplicating eight isolated comments. That reflects how reviewers actually think: a continuity error is one issue with duration, not a collection of unrelated mistakes.

06 / QUALITYQuality assurance stays inside the geometry

Many tools treat quality assurance as a separate destination. That separation is organizationally neat and operationally expensive: the reviewer loses the annotator's context, and the annotator later receives a vague list of errors detached from the scene. Here, annotation, review, repair, and acceptance share the same workspace.

Annotation completeThe scene is ready for review.
Quality passedGeometry and labels are accepted.
Quality failedSpecific repair work is attached.
Data acceptedThe task can enter the dataset.

Review findings appear as numbered markers in the 3D scene and as entries in the issue panel. The marker supplies location; the panel supplies description, conversation, and resolution state. A repair confirmation—“confirmed fixed for the issue above”—closes the loop without forcing the operator to reconstruct what the reviewer saw.

Color carries review state only when it can be read without opening a panel. For an unselected box, light gray means annotated but not reviewed, light blue means reviewed and accepted, and light red means reviewed but failed. A failed object therefore asks for attention from the scene itself.

Not reviewedAnnotated, waiting for quality inspection.
PassedInspected and accepted by quality review.
FailedInspected, rejected, and linked to a repair issue.

“Unknown” is a responsible answer

The unknown class is treated as a first-class state rather than a shameful exception. Point clouds are incomplete by nature: occlusion, sparse returns, and unfamiliar equipment can make certainty impossible. Giving uncertainty a visible, legitimate path prevents operators from forcing a confident but incorrect label merely to continue. Good annotation software does not hide ambiguity; it contains it.

07 / LANGUAGEA light, modern studio—not a heavy enterprise console

The visual language borrows the nimble feeling of a modern design tool. It uses a dark working canvas, restrained chrome, crisp one-pixel separators, compact icon-led controls, and selection color that feels immediate rather than ceremonial. Panels sit beside one another instead of becoming stacks of cards. Space is reserved for data, not decoration.

The darkness is functional: point returns, wireframes, labels, and box edges need strong local contrast. Saturated class colors remain legible against black while the surrounding interface recedes. Blue is reserved for active or accepted states; red is reserved for failure; yellow and violet retain their power as object identities because they are not reused casually for unrelated messages.

Class identity is vivid; structural UI remains quiet.

This is where “lightness” matters. It does not mean fewer capabilities or more empty space. It means fast response, shallow hierarchy, visible causality, and controls that feel close to the object they affect. The interface should feel like a studio instrument: precise, lively, and ready to be handled.

08 / LEARNINGDesigning the learning curve

A new operator should not have to understand the entire production pipeline before drawing a useful box. The stable workspace lets learning happen in layers. First, select an instance and recognize its highlight. Next, adjust the box in the projections. Then use the inspector. Finally, understand temporal continuity and review states. Each new concept attaches to a place the operator already knows.

Repetition then becomes muscle memory. The same actions produce the same visible consequences. The active object is always blue in the list. The inspector is always on the right. The playhead is always below the scene. A review problem is always both spatial and textual. This predictability is more valuable than a clever shortcut that must be remembered.

Why the discarded drafts mattered

The design exploration deliberately kept rejected timeline and dashboard variants beside the final direction. Earlier approaches separated progress, objects, and status into more independent surfaces. They could display more at once, but they fragmented the operator's loop. The final layout wins by making fewer conceptual borders: one selected instance, one current frame, one shared status, many synchronized views.

09 / SYSTEMThe system behind the screen

The interface can be summarized as a set of reusable product principles. They apply beyond point clouds—to any expert tool where people make many small decisions against complex visual evidence.

  1. 01Optimize the repeated path before polishing the exceptional path.
  2. 02Give every kind of information a stable spatial home.
  3. 03Let one selection synchronize every representation of an object.
  4. 04Expose time as structure, not merely as a frame number.
  5. 05Keep review feedback attached to the exact geometry and duration it describes.
  6. 06Use color for identity and state only when it survives peripheral vision.
  7. 07Treat uncertainty as information the system should preserve.

The deepest design move is not a panel, a color, or a timeline. It is the decision to model the operator's work as one continuous flow. Annotation creates evidence. Quality review interprets it. Repair returns to the same evidence. Data acceptance closes the same thread. The interface keeps that continuity visible.

The best annotation tool is not the one with the most visible power. It is the one that lets skilled judgment move with the least resistance.
